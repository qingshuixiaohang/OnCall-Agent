      A --> E[vector_store_manager]

After：一个 RAGPipeline 深模块
flowchart LR

问题：接口复杂度 ≈ 实现复杂度，调用方要理解 8 个服务的协作方式，新增检索策略需改多处。
方案：抽一个 RAGPipeline 深模块，对外只暴露 query() 和 ingest()，内部细节封装。
  • 测试只需 mock 一个接口
  • Milvus/关键词/重排的切换不再泄漏到调用方
  • 新增检索策略只需改模块内部

2. MCP 客户端缺少 Adapter 层

Worth exploring
app/agent/mcp_client.py · planner.py · executor.py · supervisor.py
Before：业务代码直接依赖 MCP 协议
flowchart TD
      A[Planner] --> B[MCP 协议调用]
      C[Executor] --> B
      D[Supervisor] --> B
      B --> E[CLS Server]
      B --> F[Monitor Server]
      B -.leak.-> G[tool_name / arguments / transport]
      classDef leak stroke:#dc2626,stroke-width:2px,fill:#fef2f2;
      class G leak
After：MCP Adapter 封装协议细节
flowchart LR
      A[Planner] --> C[LogAdapter]
      C --> B[MCP 协议调用]
      D[Executor] --> C
      E[Supervisor] --> C
      C -.seam.-> F[CLS / Monitor]
      classDef deep fill:#0f172a,color:#fff;
      class C deep
问题：Planner/Executor/Supervisor 直接拼 MCP 工具名和参数，协议细节泄漏到业务逻辑。
方案：引入 LogAdapter / MonitorAdapter，业务代码只喊"查日志"/"查监控"，不关心底层是 MCP 还是 REST。
  • 切换数据源只需改 Adapter
  • 业务测试不再需要 MCP server 运行
  • 降级/重试逻辑集中在一处

3. 诊断状态定义分散

Speculative
app/agent/aiops/state.py · app/agent/multi_agent/state.py · app/models/aiops.py
Before：两套状态各管各的
flowchart TD
      A[aiops/state.py] --> B[AIOpsState]
      C[multi_agent/state.py] --> D[MultiAgentState]
      B -.leak.-> E[diagnosis_history]
      D -.leak.-> E
      E -.leak.-> F[跨工作流复用]
      classDef leak stroke:#dc2626,stroke-width:2px,fill:#fef2f2;
      class E leak
After：统一 DiagnosisState 基类
flowchart LR
      A[DiagnosisState] --> B[AIOpsState]
      A --> C[MultiAgentState]
      B --> D[planner/executor/replanner]
      C --> E[supervisor/specialists]
      classDef deep fill:#0f172a,color:#fff;
              class A deep
问题：两个工作流各自维护状态结构，diagnosis_history、time_context 等字段可能重复定义。
方案：抽一个 DiagnosisState 基类，共享受诊历史和上下文管理。
  • 消除状态结构重复
  • 新增工作流类型只需继承基类

🎯 优先推荐：RAG 服务层收拢

这是最强信号：8 个服务文件，调用方手动组装，接口复杂度接近实现复杂度。收拢后测试面、替换成本、新增策略的成本都大幅下降。建议从这里开始深化。
