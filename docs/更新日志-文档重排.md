# 更新日志 — 文档重排（Rerank）功能

> **日期**: 2026-06-04
> **功能**: 在 RAG 检索管道中新增语义重排（Rerank）环节
> **状态**: ✅ 已完成

---

## 一、功能概述

### 改动前：单阶段检索

```
用户 Query → 向量检索 (similarity_search k=3) → 格式化 → 返回给 LLM
```

**问题**：向量检索基于向量空间距离（L2/IP），只能捕捉"表面相似"，无法精准理解"语义相关性"。例如用户问"CPU 过高怎么办"，向量检索可能返回的是"内存过高处理方案"，因为两个文档的向量在空间中比较接近。

### 改动后：两阶段检索 + 重排

```
用户 Query → 粗排 (向量检索 k=9) → 精排 (重排模型 top_n=3) → 格式化 → 返回给 LLM
```

**优势**：
- 粗排阶段多召回一些候选（9 篇），保证召回率（Recall）
- 精排阶段用专用重排模型做语义级精准排序，保证精确率（Precision）
- 最终返回给 LLM 的 3 篇文档质量显著提升

---

## 二、核心原理：为什么重排比纯向量检索更准？

| 对比维度 | 向量检索（粗排） | 重排模型（精排） |
|---------|----------------|----------------|
| **判断依据** | 向量空间距离（L2/内积） | 交叉编码器（Cross-Encoder）的深度语义理解 |
| **计算方式** | 独立计算 query 和 doc 各自的向量，然后算距离 | 将 query + doc 拼接后一起送入模型推理 |
| **精度** | 快但粗糙 | 慢但精准 |
| **模型** | text-embedding-v4（Embedding 模型） | gte-rerank（Rerank 模型） |
| **适用场景** | 大范围初筛 | 小范围精排 |

**一句话解释**：向量检索是"一眼扫过去找相似的"，重排是"仔细读一遍挑最相关的"。

### 3.3 `app/services/rerank_service.py` — 新建重排服务（核心）

**文件路径**: [`app/services/rerank_service.py`](app/services/rerank_service.py)

**这是本次改动最核心的新文件。** 它封装了与阿里云百炼 DashScope Rerank API 的交互。

#### 类结构

```python
class RerankService:
    """文档重排服务 — 调用阿里云百炼 DashScope Rerank API"""

    def __init__(self):
        self.api_key = config.dashscope_api_key      # 复用 DashScope API Key
        self.model = config.rerank_model             # "gte-rerank"
        self.retrieval_k = config.rag_retrieval_k    # 9
        self.top_k = config.rag_top_k                # 3
        self._client: httpx.Client | None = None     # HTTP 客户端（延迟创建）

    @property
    def client(self) -> httpx.Client:
        """延迟创建 httpx 客户端（带连接池复用和 30 秒超时）"""

    def rerank(self, query: str, documents: List[Document]) -> List[Document]:
        """核心方法：对文档列表进行语义重排"""

    def close(self) -> None:
        """关闭 HTTP 客户端连接池"""
```

#### `rerank()` 方法工作流程

```
输入: query="CPU使用率过高如何处理", documents=[9个Document对象]

步骤1: 从 Document.page_content 提取 9 段文本
步骤2: 构建 POST 请求到 DashScope Rerank API
       {
         "model": "gte-rerank",
         "input": {
           "query": "CPU使用率过高如何处理",
           "documents": ["文档1内容", "文档2内容", ...]
         },
         "parameters": {
           "top_n": 3,
           "return_documents": false
         }
       }
步骤3: 发送请求并解析响应
       {
         "output": {
           "results": [
             {"index": 2, "relevance_score": 0.95},
             {"index": 0, "relevance_score": 0.82},
             {"index": 5, "relevance_score": 0.71}
           ]
         }
       }
步骤4: 按 relevance_score 降序排列
步骤5: 用 index 映射回原始 Document 对象
步骤6: 在 Document.metadata 中附加 rerank_score 和 rerank_model

输出: 3个按相关性排序的Document对象
```

#### 关键设计决策

| 决策 | 实现 | 原因 |
|------|------|------|
| HTTP 库 | `httpx` | 已是项目依赖（FastAPI 自带），同步客户端，不需要 async |
| 客户端管理 | 延迟创建 + 属性 (property) | 只在首次调用 `rerank()` 时创建连接，避免模块导入时的副作用 |
| 失败策略 | 直接抛出 `RuntimeError` | 按需求"不降级" |
| 跳过条件 | `len(docs) <= top_k` 时直接返回 | 无需重排，省一次 API 调用 |
| 元数据附加 | `doc.metadata["rerank_score"]` | 供 `format_docs()` 使用，让 LLM 看到每篇文档的相关性标签 |
| API 端点 | `dashscope.aliyuncs.com/api/v1/services/rerank/text-rerank/text-rerank` | 阿里云百炼官方端点 |

#### 异常处理层次

```
httpx.HTTPStatusError  → RuntimeError("重排 API 调用失败 (HTTP {code}): {body}")
httpx.RequestError     → RuntimeError("重排 API 网络请求失败: {e}")
其他 Exception          → RuntimeError("文档重排失败: {e}")
ValueError             → 直接抛出（API Key 未配置）
```

### 3.4 `app/tools/knowledge_tool.py` — 集成重排逻辑

**文件路径**: [`app/tools/knowledge_tool.py`](app/tools/knowledge_tool.py)

#### 改动前（旧代码）

```python
# 从向量存储中检索相关文档
vector_store = vector_store_manager.get_vector_store()
retriever = vector_store.as_retriever(
    search_kwargs={"k": config.rag_top_k}  # k=3
)
docs = retriever.invoke(query)
```

#### 改动后（新代码）

```python
# ========== 阶段1: 粗排（向量检索多召回） ==========
vector_store = vector_store_manager.get_vector_store()
retrieval_k = config.rag_retrieval_k  # 9
docs = vector_store.similarity_search(query, k=retrieval_k)

# ========== 阶段2: 精排（重排模型筛选） ==========
top_k = config.rag_top_k  # 3
if len(docs) > top_k:
    docs = rerank_service.rerank(query, docs)
```

#### 改动要点

1. **检索方式变更**: `as_retriever().invoke()` → `similarity_search()`，因为我们需要灵活控制 k 值
2. **检索数量变更**: `rag_top_k`(3) → `rag_retrieval_k`(9)，多召回 3 倍的候选文档
3. **新增重排步骤**: 检索后调用 `rerank_service.rerank()` 进行精排
4. **新增异常处理**: 重排失败时 `RuntimeError` 直接向上传播（不降级），其他异常保持原有降级逻辑
5. **新增 `_score_to_label()` 辅助函数**: 将重排分数 (0.0-1.0) 转换为可读标签（⭐⭐⭐ 高度相关 等），在 `format_docs()` 中展示

#### 格式化输出的变化

改动前：
```
【参考资料 1】
来源: cpu_high_usage.md
内容:
CPU使用率过高的处理方案...
```

改动后（有重排分数时）：
```
【参考资料 1】
来源: cpu_high_usage.md
相关性: ⭐⭐⭐ 高度相关 (0.9500)
内容:
CPU使用率过高的处理方案...
```

这样 LLM 能根据相关性标签判断每篇文档的可信度。

## 五、配置参数调优指南

| 参数 | 默认值 | 含义 | 调优建议 |
|------|--------|------|---------|
| `RERANK_MODEL` | `gte-rerank` | 重排模型 | 可选 `gte-rerank-v2`（更新版），在 `.env` 中修改 |
| `RAG_TOP_K` | `3` | 最终返回给 LLM 的文档数 | 建议 3-5，太多会撑满 LLM 上下文窗口 |
| `RAG_RETRIEVAL_K` | `9` | 粗排召回数 | 建议为 `RAG_TOP_K` 的 2-5 倍。越大召回率越高但 API 消耗也越高 |

**调优示例**：
- 如果知识库文档较少（<20 篇）：`RAG_RETRIEVAL_K=6`（2 倍）
- 如果知识库文档较多（>100 篇）：`RAG_RETRIEVAL_K=15`（5 倍）
- 如果对精度要求极高：`RAG_TOP_K=5`, `RAG_RETRIEVAL_K=15`

## 六、故障排查

### 问题 1：重排 API 调用失败

**现象**: 日志中出现 `RerankService: DashScope API 返回错误状态码`

**原因**:
1. `DASHSCOPE_API_KEY` 未配置或已过期
2. 模型名称错误（如写成了 `gte_rerank` 而不是 `gte-rerank`）
3. API 额度用尽

**解决**:
```bash
# 检查 .env 配置
type .env | findstr DASHSCOPE

# 确认 API Key 有效
curl -X POST https://dashscope.aliyuncs.com/api/v1/services/rerank/text-rerank/text-rerank \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"gte-rerank","input":{"query":"test","documents":["test doc"]},"parameters":{"top_n":1}}'
```

### 问题 2：重排分数都很低（<0.3）

**现象**: 所有文档的重排分数都低于 0.3

**原因**: 向量检索召回的候选文档与查询确实不太相关

**解决**: 增大 `RAG_RETRIEVAL_K`（如从 9 改为 15），让粗排阶段召回更多候选
