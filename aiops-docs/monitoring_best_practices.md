## 监控体系设计

### 监控层次

#### 1. 基础设施层监控
**监控对象**: 服务器、网络、存储等基础设施

**关键指标**:
- **CPU**: 使用率、负载、上下文切换
- **内存**: 使用率、可用内存、Swap使用
- **磁盘**: 使用率、IOPS、IO等待
- **网络**: 带宽、延迟、丢包率、连接数

**监控工具**:
- Prometheus + Node Exporter
- Zabbix
- Nagios
- CloudWatch（AWS）/ 云监控（阿里云）

#### 2. 中间件层监控
**监控对象**: 数据库、缓存、消息队列等中间件

**关键指标**:

**数据库**:
- QPS/TPS
- 连接数使用率
- 慢查询数量
- 缓存命中率
- 锁等待时间

**Redis**:
- 内存使用率
- 键驱逐数量
- 缓存命中率
- 客户端连接数
- 持久化状态

**MQ**:
- 队列长度
- 消息生产/消费速率
- 消费者数量
- 消息延迟
- 死信队列数量

**监控工具**:
- Prometheus + Exporters
- 自带监控工具（Redis INFO、RabbitMQ Management）
- 商业APM工具

#### 3. 应用层监控
**监控对象**: 应用服务、API接口

**关键指标**:
- **可用性**: 健康检查成功率、HTTP状态码
- **性能**: 响应时间（P50/P95/P99）、吞吐量（QPS/TPS）
- **错误**: 错误率（4xx/5xx）、异常数量
- **资源**: JVM/进程内存、线程数、GC情况

**监控工具**:
- Prometheus + Micrometer（Java）
- StatsD + Grafana
- New Relic / Datadog
- SkyWalking / Jaeger（链路追踪）

#### 4. 业务层监控
**监控对象**: 业务指标、用户体验

**关键指标**:
- **用户行为**: DAU/MAU、页面访问量、停留时间
- **业务流程**: 订单量、支付成功率、转化率
- **业务异常**: 订单失败、支付失败、登录失败
- **用户体验**: 页面加载时间、接口响应时间、错误提示

**监控工具**:
- Google Analytics
- 自建埋点系统
- 业务日志分析
- 用户反馈系统

### 监控架构

```
┌─────────────────────────────────────────┐
│         监控数据采集层                  │

                    ↓
```

## 监控指标分类

### 指标类型

#### 1. 计数器（Counter）
**定义**: 只增不减的累积值
**示例**:
- 请求总数
- 错误总数
- 消息生产数量

**使用场景**:
```prometheus
# HTTP请求总数
http_requests_total{method="POST", endpoint="/api/order"}

# 错误总数
http_errors_total{status="500"}

# 计算错误率
rate(http_errors_total[5m]) / rate(http_requests_total[5m])
```

#### 2. 仪表盘（Gauge）
**定义**: 可增可减的瞬时值
**示例**:
- CPU使用率
- 内存使用率
- 当前连接数
- 队列长度

**使用场景**:
```prometheus
# CPU使用率
cpu_usage_percent

# 内存使用率
memory_usage_percent

# 当前连接数
db_connections_active
```

#### 3. 直方图（Histogram）
**定义**: 观测值分布，通常用于响应时间
**示例**:
- 响应时间分布
- 请求大小分布

**使用场景**:
```prometheus
# 响应时间直方图
http_request_duration_seconds_bucket{le="0.1"}
http_request_duration_seconds_bucket{le="0.5"}
http_request_duration_seconds_bucket{le="1.0"}

# 计算P95响应时间
histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[5m]))
```

#### 4. 摘要（Summary）
**定义**: 类似直方图，但计算分位数
**示例**:
- 响应时间分位数

**使用场景**:
```prometheus
# 响应时间摘要
http_request_duration_seconds{quantile="0.95"}
http_request_duration_seconds{quantile="0.99"}
```

### 黄金指标（Four Golden Signals）

#### 1. 延迟（Latency）
**定义**: 请求处理时间
**指标**:
- 平均响应时间
- P50/P95/P99响应时间
- 按端点分类的延迟

**告警阈值建议**:
- 警告: P95 > 1s
- 严重: P95 > 3s
- 紧急: P95 > 5s

#### 2. 流量（Traffic）
**定义**: 系统负载度量
**指标**:
- QPS（每秒查询数）
- TPS（每秒事务数）
- 并发请求数

**告警阈值建议**:
- 基于历史峰值设置
- 突然下降50%以上告警
- 超过容量阈值告警

#### 3. 错误（Errors）
**定义**: 失败请求的比例
**指标**:
- 错误率（4xx/5xx比例）
- 失败请求数
- 按错误类型分类

**告警阈值建议**:
- 警告: 错误率 > 0.5%
- 严重: 错误率 > 1%
- 紧急: 错误率 > 5%

#### 4. 饱和度（Saturation）
**定义**: 系统容量使用情况
**指标**:
- CPU使用率
- 内存使用率
- 磁盘使用率
- 连接池使用率
- 队列长度

**告警阈值建议**:
- 警告: 使用率 > 70%
- 严重: 使用率 > 85%
- 紧急: 使用率 > 95%

### RED方法（针对服务）
- **Rate**: 请求速率
- **Errors**: 错误率
- **Duration**: 响应时间分布

### USE方法（针对资源）
- **Utilization**: 资源使用时间百分比
- **Saturation**: 资源队列长度或等待数量
- **Errors**: 错误计数

## 告警策略配置

### 告警分级

#### P0 - 紧急告警
**定义**: 核心业务完全中断
**示例**:
- 服务完全不可用（健康检查失败率 > 50%）
- 数据库主库宕机
- 数据丢失风险

**配置**:
- 持续时间: 1分钟
- 通知方式: 电话 + 短信 + 钉钉
- 升级机制: 15分钟未处理升级到总监

#### P1 - 严重告警
**定义**: 核心业务严重受损
**示例**:
- 错误率 > 5%
- P99响应时间 > 10s
- 缓存完全失效

**配置**:
- 持续时间: 3分钟
- 通知方式: 电话 + 钉钉
- 升级机制: 30分钟未处理升级到总监

#### P2 - 高优先级告警
**定义**: 核心业务性能下降
**示例**:
- 错误率 > 1%
- P99响应时间 > 5s
- CPU使用率 > 90%

**配置**:
- 持续时间: 5分钟
- 通知方式: 钉钉
- 升级机制: 1小时未处理升级到技术负责人

#### P3 - 中优先级告警
**定义**: 非核心业务问题
**示例**:
- 非核心接口错误率 > 2%
- 磁盘使用率 > 80%
- 队列长度异常

**配置**:
- 持续时间: 10分钟
- 通知方式: 钉钉
- 升级机制: 4小时未处理升级到技术负责人

#### P4 - 低优先级告警
**定义**: 轻微问题或优化建议
**示例**:
- 性能轻微下降
- 监控指标异常趋势
- 资源使用率预警

**配置**:
- 持续时间: 30分钟
- 通知方式: 邮件
- 升级机制: 次日处理

### 告警配置最佳实践

#### 1. 避免告警风暴
**问题**: 大量告警同时触发，无法有效处理
**解决方案**:
```yaml
# 告警分组
group_by: ['alertname', 'cluster', 'service']

# 分组等待时间
group_wait: 30s

# 分组间隔
group_interval: 5m

# 重复告警间隔
repeat_interval: 4h
```

#### 2. 告警抑制
**目的**: 避免重复告警
**示例**:
- 服务不可用时，抑制该服务的所有其他告警
- 网络故障时，抑制所有依赖网络的告警

```yaml
# 抑制规则
inhibit_rules:
  - source_match:
      severity: 'critical'
    target_match:
      severity: 'warning'
    equal: ['service']
```

#### 3. 告警去重
**目的**: 相同告警只通知一次
```yaml
# 在有效期内只发送一次告警
repeat_interval: 4h
```

#### 4. 告警路由
**目的**: 正确通知到责任人
```yaml
# 按服务路由
route:
  receiver: 'default'
  routes:
    - match:
        service: 'order'
      receiver: 'order-team'
    - match:
        service: 'payment'
      receiver: 'payment-team'
```

### 告警阈值设置

#### 基于百分位
```promql
# CPU使用率超过90%
cpu_usage_percent > 90

# P99响应时间超过3s
histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m])) > 3
```

#### 基于同比/环比
```promql
# 错误率比上周同一时间高2倍
rate(http_errors_total[5m]) > 2 * rate(http_errors_total[5m] offset 1w)

# QPS比昨天下降50%
rate(http_requests_total[5m]) < 0.5 * rate(http_requests_total[5m] offset 1d)
```

#### 基于趋势预测
```promql
# 预测1小时后磁盘将满
predict_linear(dfree_bytes[1h], 4 * 3600) < 0
```

## 监控工具选型

### 指标监控

#### Prometheus + Grafana（推荐）
**优势**:
- 开源免费
- 生态丰富，支持大量Exporter
- 强大的查询语言（PromQL）
- Grafana可视化效果好
- 社区活跃

**适用场景**:
- 云原生应用
- 微服务架构
- 容器化部署

**生态组件**:
- Prometheus: 指标采集和存储
- Grafana: 可视化Dashboard
- Alertmanager: 告警管理
- Node Exporter: 服务器指标
- JMX Exporter: JVM指标
- Redis Exporter: Redis指标
- MySQL Exporter: MySQL指标

#### InfluxDB + Grafana
**优势**:
- 时序数据库性能好
- 支持高基数数据
- 数据保留策略灵活

**适用场景**:
- 大规模时序数据
- 长期数据存储
- 自定义指标

**优势**:
- 功能强大
- 搜索和分析能力强

**优势**:

**适用场景**:
- 中小型微服务
- 快速上手

### APM（应用性能监控）

**优势**:

**适用场景**:
- Java应用

**优势**:

## 告警处理流程

### 告警响应流程

#### 1. 告警接收
- 接收告警通知（电话/短信/钉钉）
- 查看告警详情
- 确认告警级别

#### 2. 告警确认
- 登录监控平台查看Dashboard
- 分析监控图表
- 确认告警真实性
- 评估影响范围

#### 3. 告警处理
- 根据告警级别启动相应流程
- 执行止损措施
- 定位问题原因
- 解决问题

#### 4. 告警恢复
- 确认问题已解决
- 验证监控指标恢复正常
- 通知相关人员
- 记录处理过程

#### 5. 告警复盘
- 分析告警原因
- 总结经验教训
- 优化告警配置
- 更新知识库

### 告警升级机制

```
时间
0min   → 值班工程师响应
15min  → 未恢复 → 技术负责人
30min  → 未恢复 → 部门总监
1hour  → 未恢复 → CTO / 最高应急响应
```

### 告警On-Call机制

#### On-Call排班
- 7x24小时轮值
- 明确值班人员
- 提前通知
- 备用人员

#### On-Call职责
- 及时响应告警
- 按流程处理故障
- 记录处理过程
- 升级和求助

#### On-Call支持
- 值班手册
- 故障处理Checklist
- 专家联系方式
- 自动化工具

## 监控优化建议

### 1. Dashboard设计最佳实践

- 服务可用性
- 延迟（P50/P95/P99）
- 流量（QPS/TPS）

- 合并相关告警
- 抑制重复告警
- 合理设置持续时间
- 定期清理无效告警

#### 告警精准化
- 基于业务特征设置告警
- 区分工作日和节假日
- 区分业务高峰和低谷
- 动态调整告警阈值

#### 告警智能化
- 异常检测算法
- 机器学习预测
- 自动根因分析
- 智能告警降噪

### 3. 监控数据优化

#### 数据保留策略
```yaml
# Prometheus数据保留
global:
  scrape_interval: 15s
  evaluation_interval: 15s
  external_labels:
    monitor: 'prometheus'
  storage:
    tsdb:
      retention.time: 30d  # 保留30天详细数据
      retention.size: 50GB # 保留50GB数据
```

#### 数据聚合
- 高频数据降采样
- 历史数据归档
- 热数据和冷数据分离

### 4. 成本优化

#### 降低监控成本
- 合理设置采集频率
- 控制标签数量（避免高基数）
- 数据压缩
- 冷数据归档

#### 云服务优化
- 使用云监控服务
- 合理配置保留期
- 选择合适的存储类型

### 5. 监控可观测性

#### 可观测性三大支柱
1. **Metrics（指标）**: 量化数据，趋势分析
2. **Logs（日志）**: 详细记录，问题排查

#### 可观测性最佳实践

- 关联分析
- 上下文丰富
- 快速查询

### 6. 监控自动化

## 常见问题

### Q: 告警太多，如何处理？
A:
1. 合并相关告警
2. 提高告警阈值
3. 增加持续时间
4. 抑制重复告警
5. 分级处理

### Q: 告警不准确，误报太多？
A:
1. 优化告警阈值
2. 增加持续时间
3. 多维度验证
4. 机器学习降噪
5. 定期优化告警规则

### Q: 监控数据延迟严重？
A:
1. 检查采集频率
2. 优化采集性能
3. 增加采集节点
