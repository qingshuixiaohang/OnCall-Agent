## 故障排查通用流程

### 阶段1: 发现和确认（0-2分钟）

#### 目标
确认故障的真实性和影响范围

#### 关键步骤
1. **接收告警**: 通过监控系统、用户反馈、值班电话等渠道接收告警
2. **确认告警**: 验证告警的真实性，排除误报
   - 检查监控图表和指标
   - 查看相关日志
   - 进行快速测试确认
3. **评估影响**: 确定故障的影响范围和严重程度
   - 受影响的服务
   - 受影响用户数量
   - 业务影响程度
   - 数据安全风险

#### 检查清单
- [ ] 告警已确认，不是误报
- [ ] 故障时间已记录
- [ ] 影响范围已评估
- [ ] 故障级别已确定
- [ ] 相关人员已通知

### 阶段2: 止损和隔离（2-10分钟）

#### 目标
快速止损，防止故障扩大

#### 关键步骤
1. **启动应急**: 根据故障级别启动相应的应急响应流程
2. **快速止损**:
   - 重启故障服务
   - 摘除故障实例
   - 启用降级策略
   - 关闭有问题的功能
3. **隔离故障**:
   - 隔离受影响的服务
   - 防止故障扩散到其他系统
   - 保护数据安全
4. **信息同步**: 向相关团队同步故障信息

#### 止损策略优先级
1. **重启**: 快速恢复服务
2. **回滚**: 回滚到上一个稳定版本
3. **降级**: 关闭非核心功能
4. **切换**: 切换到备用系统
5. **限流**: 保护系统不被压垮

#### 检查清单
- [ ] 止损措施已执行
- [ ] 故障已隔离
- [ ] 影响范围已控制
- [ ] 用户已通知（如需要）
- [ ] 团队已同步信息

### 阶段3: 定位根因（10-30分钟）

#### 目标
找出故障的根本原因

#### 关键步骤
1. **收集信息**:
   - 查看监控图表（CPU、内存、磁盘、网络）
   - 分析日志（应用日志、系统日志、错误日志）
   - 检查最近的变更（代码发布、配置变更、数据变更）
   - 查看依赖服务状态

2. **分析推理**:
   - 使用5Why分析法找出根本原因
   - 分析故障时间线和影响范围
   - 对比正常和异常状态
   - 排除不可能的原因

3. **验证假设**:
   - 提出可能的原因假设
   - 设计验证方案
   - 逐步验证假设
   - 确认根本原因

#### 排查方法论

##### 自上而下法
1. 从用户端开始排查
2. 逐层向下深入到系统内部
3. 适合排查用户体验问题

##### 自下而上法
1. 从底层基础设施开始
2. 逐层向上到应用层
3. 适合排查系统底层问题

##### 对比法
1. 对比正常和异常状态
2. 找出差异点
3. 定位问题所在

##### 二分法
1. 将系统分成两部分
2. 确定问题在哪部分
3. 递归缩小范围

#### 检查清单
- [ ] 已收集所有相关信息
- [ ] 已分析监控和日志
- [ ] 已检查最近的变更
- [ ] 已验证根本原因
- [ ] 已记录排查过程

### 阶段4: 解决问题（30分钟-2小时）

#### 目标
彻底解决问题并恢复服务

#### 关键步骤
1. **制定方案**: 根据根本原因制定解决方案
2. **评估风险**: 评估解决方案的风险和影响
3. **实施方案**: 
   - 优先选择风险最小的方案
   - 必要时进行测试验证
   - 逐步实施，随时准备回滚
4. **验证效果**: 确认问题已解决
5. **监控观察**: 持续监控确保稳定

#### 解决方案优先级
1. **临时方案**: 快速恢复服务，后续再彻底解决
2. **配置调整**: 调整配置参数
3. **代码修复**: 修复代码bug
4. **架构优化**: 长期架构改进

#### 检查清单
- [ ] 解决方案已确定
- [ ] 风险评估已完成
- [ ] 解决方案已实施
- [ ] 问题已验证解决
- [ ] 服务已恢复正常

### 阶段5: 恢复和验证（1-2小时）

#### 目标
全面恢复服务并验证正常

#### 关键步骤
1. **逐步恢复**:
   - 先恢复核心功能
   - 再恢复非核心功能
   - 分批恢复，监控每批效果

2. **全面验证**:
   - 功能测试
   - 性能测试
   - 压力测试
   - 数据一致性检查

3. **监控观察**:
   - 持续监控关键指标
   - 关注错误率和性能
   - 观察用户反馈

#### 检查清单
- [ ] 核心功能已恢复
- [ ] 非核心功能已恢复
- [ ] 性能指标正常
- [ ] 错误率正常
- [ ] 用户反馈良好

### 阶段6: 总结和改进（2-24小时）

#### 目标
总结经验，防止同类故障再次发生

#### 关键步骤
1. **故障复盘**:
   - 整理故障时间线
   - 分析根本原因
   - 评估影响和损失
   - 总结经验教训

2. **改进措施**:
   - 制定短期改进措施（1周内）
   - 制定长期改进措施（1个月内）
   - 分配责任人和时间节点
   - 跟踪改进措施执行

3. **文档更新**:
   - 更新故障处理手册
   - 更新应急预案
   - 更新监控告警配置
   - 分享经验教训

#### 检查清单
- [ ] 故障复盘已完成
- [ ] 改进措施已制定
- [ ] 责任人已分配
- [ ] 文档已更新
- [ ] 经验已分享

## 故障分类和优先级

### 故障级别定义

#### P0 - 紧急（Emergency）
**定义**: 核心业务完全中断，影响所有用户
**特征**:
- 服务完全不可用
- 数据丢失风险
- 安全漏洞被利用
- 影响所有用户

**响应要求**:
- 15分钟内响应
- 1小时内恢复
- 立即升级到管理层
- 所有相关人员参与

#### P1 - 严重（Critical）
**定义**: 核心业务部分中断，影响大部分用户
**特征**:
- 核心功能不可用
- 部分用户受影响
- 数据不一致
- 性能严重下降

**响应要求**:
- 30分钟内响应
- 2小时内恢复
- 技术负责人参与
- 相关团队协作

#### P2 - 高（High）
**定义**: 非核心业务中断或核心业务性能下降
**特征**:
- 非核心功能不可用
- 部分功能异常
- 性能下降但可用
- 影响少量用户

**响应要求**:
- 1小时内响应
- 4小时内恢复
- 开发团队处理
- 定期汇报进度

#### P3 - 中（Medium）
**定义**: 轻微问题，不影响核心业务
**特征**:
- 边缘功能异常
- 监控告警
- 性能轻微下降
- 无用户影响

**响应要求**:
- 4小时内响应
- 24小时内恢复
- 常规处理流程
- 记录和处理

#### P4 - 低（Low）
**定义**: 优化建议或轻微问题
**特征**:
- 用户体验轻微影响
- 代码优化建议
- 文档更新需求
- 技术债务

**响应要求**:
- 按计划处理
- 纳入迭代计划
- 常规优先级

### 故障类型分类

#### 按影响范围
- **全局故障**: 影响所有用户和服务
- **局部故障**: 影响部分用户或服务
- **单点故障**: 影响单个实例或组件

#### 按业务影响
- **核心业务故障**: 影响主要业务流程
- **非核心业务故障**: 影响辅助功能
- **用户体验故障**: 影响用户体验但不影响功能

#### 按技术领域
- **应用层故障**: 代码、业务逻辑问题
- **中间件故障**: 数据库、缓存、MQ等
- **基础设施故障**: 服务器、网络、存储等
- **第三方故障**: 依赖的外部服务

## 故障排查方法论

### 5Why分析法

#### 什么是5Why
通过连续追问"为什么"来找出问题的根本原因

#### 使用步骤
1. 定义问题
2. 问第一个为什么
3. 回答后继续问为什么
4. 重复3-5次
5. 找到根本原因
6. 制定纠正措施

#### 示例
```
问题: 服务器CPU使用率100%

Why 1: 为什么CPU使用率100%?
Answer: 因为某个进程占用了100% CPU

Why 2: 为什么进程占用100% CPU?
Answer: 因为代码中有死循环

Why 3: 为什么有死循环?
Answer: 因为边界条件处理错误

Why 4: 为什么边界条件处理错误?
Answer: 因为单元测试没有覆盖边界情况

Why 5: 为什么单元测试没有覆盖?
Answer: 因为测试用例评审不严格

根本原因: 测试流程不完善
纠正措施: 加强测试用例评审，要求覆盖边界条件
```

### 鱼骨图分析法

#### 结构
```
                        问题
                         |
        -------------------------------------------------
        |          |          |         |                |
      人员       机器       方法      环境              材料
        |          |          |         |                |
    ...        ...        ...       ...               ...
```

#### 应用场景
- 复杂问题分析
- 多因素影响
- 团队讨论和头脑风暴

### SWOT分析

#### 要素
- **Strengths**: 优势（什么工作正常）
- **Weaknesses**: 劣势（什么不正常）
- **Opportunities**: 机会（可以改进的地方）
- **Threats**: 威胁（潜在风险）

#### 应用
分析故障现状，找出改进方向

### 故障树分析（FTA）

#### 方法
从上到下分析故障原因：
1. 顶事件：故障现象
2. 中间事件：可能的中间原因
3. 底事件：根本原因

#### 逻辑门
- **与门(AND)**: 所有条件都满足才发生
- **或门(OR)**: 任一条件满足就发生

## 工具和命令速查

### 系统监控工具

#### CPU
```bash
# 查看CPU使用率
top -H
mpstat -P ALL 1 10
ps aux --sort=-%cpu | head -10

# 性能分析
perf top -p <pid>
perf record -g -p <pid>
```

#### 内存
```bash
# 查看内存使用
free -h
vmstat 1 10
ps aux --sort=-%mem | head -10

# Java内存分析
jmap -heap <pid>
jmap -histo <pid> | head -20
jstat -gc <pid> 1000
```

#### 磁盘
```bash
# 查看磁盘使用
df -h
du -sh /path/* | sort -hr | head -10

# 查看磁盘IO
iostat -x 1 10
iotop -p <pid>
```

#### 网络
```bash
# 网络连接
netstat -an | grep ESTABLISHED | wc -l
ss -s

# 网络性能
ping -c 10 host
traceroute host
mtr host
```

### 应用诊断工具

#### Java应用
```bash
# 线程分析
jstack <pid> > thread_dump.txt
jstack -l <pid>

# 堆内存分析
jmap -dump:format=b,file=heap.hprof <pid>
jhat heap.hprof

# GC分析
jstat -gc <pid> 1000
jstat -gccause <pid>
```

#### Python应用
```bash
# 性能分析
python -m cProfile -s time app.py
python -m memory_profiler app.py

# 调试
python -m pdb app.py
```

#### 数据库
```sql
-- MySQL
SHOW PROCESSLIST;
SHOW ENGINE INNODB STATUS;
EXPLAIN SELECT * FROM table;

-- PostgreSQL
SELECT * FROM pg_stat_activity;
SELECT * FROM pg_locks WHERE NOT granted;
```

### 日志分析工具

```bash
# 实时查看日志
tail -f app.log
multitail /var/log/*.log

# 搜索日志
grep "ERROR" app.log
grep -C 5 "Exception" app.log

# 统计分析
awk '{print $1}' access.log | sort | uniq -c | sort -nr | head -10

# 日志时间分析
awk '{print $4}' access.log | cut -d: -f1-3 | sort | uniq -c
```

### 网络诊断工具

```bash
# 连通性测试
ping host
telnet host port
nc -zv host port

# 路由跟踪
traceroute host
traceroute -T -p 443 host

# DNS诊断
nslookup domain
dig domain
host domain

# 抓包分析
tcpdump -i eth0 -w capture.pcap

```

## 最佳实践

### 监控最佳实践

#### 1. 监控覆盖
- **基础设施监控**: CPU、内存、磁盘、网络
- **应用性能监控**: 响应时间、吞吐量、错误率
- **业务监控**: 用户活跃度、交易量、转化率
- **日志监控**: 错误日志、异常模式

#### 2. 告警配置
- **合理的阈值**: 基于历史数据设置
- **告警分级**: 不同级别不同响应
- **告警收敛**: 避免告警风暴
- **告警路由**: 正确通知到人

#### 3. 监控工具
- **Prometheus + Grafana**: 指标监控
- **ELK Stack**: 日志分析
- **APM工具**: 应用性能监控
- **链路追踪**: 分布式追踪

### 故障处理最佳实践

#### 1. 快速响应
- 保持冷静，按流程处理
- 优先止损，再找原因
- 及时沟通，信息同步
- 记录过程，便于复盘

#### 2. 团队协作
- 明确角色和职责
- 统一指挥，避免混乱
- 信息共享，避免重复工作
- 及时升级，寻求帮助

#### 3. 沟通机制
- 建立战时沟通群
- 定期同步进展（每15-30分钟）
- 使用统一的故障时间线
- 及时通知相关方

#### 4. 决策原则
- 优先恢复服务
- 选择风险最小的方案
- 准备好回滚方案
- 保持可逆性

### 预防最佳实践

#### 1. 架构设计
- 高可用架构
- 故障隔离
- 降级和熔断
- 限流保护

#### 2. 发布流程
- 灰度发布
- 蓝绿部署
- 自动化测试
- 快速回滚

#### 3. 变更管理
- 变更审批
- 变更记录
- 变更回滚
- 变更后验证

#### 4. 容量规划
- 性能测试
- 容量评估
- 自动扩缩容
- 资源预警

```
确认告警真实性
  ↓
是 → 评估影响范围
  ↓
确定故障级别
  ↓
启动应急响应
  ↓
止损措施（重启/回滚/降级）
  ↓
是否恢复？
  ├─ 是 → 验证和监控 → 复盘
  └─ 否 → 定位根因 → 解决方案 → 实施 → 验证
```

### B. 故障升级矩阵

| 故障级别 | 初始响应人 | 15分钟未恢复 | 30分钟未恢复 | 1小时未恢复 |
|---------|-----------|-------------|-------------|-------------|
| P0 | 值班工程师 | 技术负责人 | 部门总监 | CTO |
| P1 | 值班工程师 | 技术负责人 | 部门总监 | CTO |
| P2 | 开发团队 | 技术负责人 | 部门总监 | - |
| P3 | 开发团队 | 技术负责人 | - | - |
| P4 | 开发团队 | - | - | - |

### C. 沟通模板

#### 故障发现通知
```
【故障发现】[服务名] 发生 [故障类型]
- 故障时间: [时间]
- 影响范围: [描述]
- 故障级别: [P0-P4]
- 当前状态: [处理中/已恢复]
- 处理人员: [姓名]
```

#### 进展同步
```
【进展同步】[服务名] 故障处理进展
- 当前时间: [时间]
- 故障持续时间: [X分钟]
- 已采取措施: [描述]
- 当前状态: [描述]
- 预计恢复时间: [时间]
```

```
【故障恢复】[服务名] 已恢复正常

- 持续时间: [X分钟]
- 影响范围: [描述]
- 根因: [原因]
- 改进措施: [措施]
```
